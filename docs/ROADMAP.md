# 实现方案

> [DESIGN.md](DESIGN.md) 说内核该长成什么样。这份说**按什么次序走到那儿，
> 每一步怎么算完成**。

---

## 0. 方法论：先撞墙，再改内核

这份计划的形状不是「列出想加的功能，排个优先级」。那样排出来的东西这个
项目已经交过两次学费：

**第一次：`Rand`。** 对着 boardgame.io 的对照表，发现「内核没有随机」是个洞，
补了一套——设计还比对照实现小一圈（流由「种子+回合+阶段」推导，不存 PRNG
进度）。**零使用者，最后删掉了。** 两套规则包的随机都发生在建局之前，局中
都不摇。

> **对照能告诉你缺什么，但告诉不了你需不需要。**
> 别人的清单反映的是别人的形态。

**第二次：差点在冻结后的 API 上继续加。** 当时的计划是「先给内核补几个
能力，再用这些能力去写阿瓦隆」，被一句话挡回来了——**「刚冻结的 API 上加东西，
不合理吧」**。改成先写阿瓦隆、内核一行不动、撞到什么记成疤，
最后七条疤全部有据可依，且其中三条与事先猜的完全不同。

**两种检验能告诉你的东西不一样，都不能省：**

| 检验 | 能告诉你 | 不能告诉你 |
|---|---|---|
| 写第二/第三套规则包 | **你真的需要什么**——它自己撞到的 | 你和它都没想到的 |
| 对照别人的实现 | **你缺什么**——别人有你没有的 | 你需不需要 |

因此本计划的次序是：**先让第三套游戏撞墙（阶段一），再一次性改内核（阶段二）。**
不先改后验，也不边改边验——那两种都会把「猜」混进「证据」里。

### 一条硬纪律

**阶段一进行中，内核一行都不许改。** 撞到的东西记进 `SCARS.md`，写下：

1. 撞到的是什么（具体到哪一条规则实现不了）
2. **绕法**（不改内核怎么先跑通）——没有绕法的才是硬伤
3. 猜想的修法
4. 归类：缺能力 / 概念错位 / 多余的特权 / 对照才看得见的

绕法这一栏是关键：能绕过去的，说明它是人机工程问题，不是抽象问题。
阿瓦隆七条疤里有两条最后判定为「绕法可以接受」，没有动内核。

## 1. 总览

| 阶段 | 目标 | 动内核吗 | 完成判据 |
|---|---|---|---|
| **一** | 第三套规则包跑通整局 | **否** | 全部结局路径有测试；疤清单成文 |
| **二** | 一次性收敛：状态模型 + 阶段一的疤 | 是 | 三套规则包全绿；疤全部关闭或明确不修 |
| **三** | 正名与文档收口 | 只改名字与注释 | 文档与代码一致；无「只写在注释里」的规矩 |
| **四** | 冻结 | 否 | 冻结检查清单全过 |

阶段二是唯一一次大改。把状态模型收敛和疤修复合并成一次，是为了**不把同一处
重构做两遍**——先改模型再写第三套，第三套的疤会长在新模型上，很可能要求
再改一次。

## 阶段一：第三套规则包，内核零改动

### 1.1 选谁

判据：**每单位工作量能证伪多少条设计假设。**

| 候选 | 会撞到什么 | 工作量 | 授权 |
|---|---|---|---|
| **一夜狼人**（推荐） | **身份可变**（夜里换牌）、**目标不是玩家**（中央的三张牌）、单夜无回合循环、同时结算 | 小（约 300 行） | 商业作品，需确认口径 |
| **Secret Hitler** | **局中随机**（政策牌堆）、总统权力=运行时行动者、两条形状不同的胜利条件、选举计数器 | 中 | 公开授权发行（**需核实条款**） |
| 血染钟楼 | 并列状态位（中毒/醉酒）、死人有票、恶魔转化 | 大 | 商业作品 |
| Spyfall | 目标是地点而非玩家 | 小 | 商业作品 |

**推荐一夜狼人**，理由是它**正对着 §8.1 那两条已有嫌疑的缺口**
（身份可变、目标不是玩家）。写完只有两种结果，都有用：

- 撞上了 → 那两条从「推测」升级为「证据」，阶段二有据可依
- 没撞上 → 说明我们对自己模型的判断有偏差，**这本身是更重要的发现**

**Secret Hitler 排第二**，因为它会直接重开「要不要随机」这个已经被删掉的
决定——而且这次是带着一局真实需求来的。它的授权方式对开源仓库也更友好，
但**条款要先核实**，不能凭印象。

### 1.2 命名与授权（**需要你定，之前问过两次没结论**）

阿瓦隆是商业桌游，一夜狼人、Secret Hitler 也是。狼人杀是民间游戏，
不存在这个问题。

事实与惯例：**玩法规则本身一般不受著作权保护，受保护的是名称、美术与
具体文字表述。** 稳妥的做法是三条一起做：

1. 包名与类型名用**描述性名字**，不用商标（比如 `resistance` 而不是 `avalon`）
2. 规则来源引用公开条目，不复制原文
3. README 写一句「本项目实现的是玩法规则，与各游戏的出版方无关」

**这条不定下来，第三套规则包不该动手**——两套已有的也要一起处理。

### 1.3 协议

照阿瓦隆那次的流程，一字不改：

```
写规则包 ──撞到 ──▶ 记进 SCARS.md（四栏：撞到什么 / 绕法 / 猜想的修法 / 归类）
    │                        │
    │                        └─▶ 绕过去，继续写
    ▼
跑通整局，全部结局路径都有测试
    │
    ▼
回头审疤：哪些是抽象问题，哪些只是人机工程
```

### 1.4 完成判据

- [ ] 规则包能从开局跑到结束，**每一条结局路径**都有测试
- [ ] 规则来源有出处（维基条目或官方规则书），与来源不一致的地方写明理由
- [ ] 内核 `git diff` 为空
- [ ] `SCARS.md` 成文，每条疤四栏齐全
- [ ] 疤按「抽象问题 / 人机工程」分好类，并给出各自的修法建议

## 阶段二：一次性收敛

输入是两份东西：§8.1 已有证据的缺口 + 阶段一的疤清单。

### 2.1 状态模型收敛成一张变量表

**这是本阶段的主干**，其余都挂在它上面。

目标（[DESIGN.md §3.1](DESIGN.md)）：

> 内核存的东西只有两样：一张变量表，和一条时间轴。
> 身份、生死、阵营都是变量表里的标准键。

具体动作：

| 今天 | 目标 |
|---|---|
| `playerState.Alive bool` | 标准键 `alive`（`ScopeGame.Of(id)`） |
| `playerState.Role RoleType` | 标准键 `role`（同上） |
| `SET_ALIVE` 一条独立原语 | 并入 `SET_VAR`，状态原语从 2 条降到 1 条 |
| `NewSetAliveEffect(id, alive)` | 保留为便利构造器，底下是 `NewSetVarEffect` |
| `Effect.SetsAlive()` | 保留，底下是 `SetsVar()` + 键名判断 |
| `PlayerInfo.Alive` / `.Role` | 保留为**派生只读字段**，快照与视图组装时填 |

**保留便利层是刻意的**：「活着的人」是最热的查询，每次做字符串比较既慢又难读。
存储收敛、读法不变——这与 `Engine` / `GameView` 两条读法并存是同一个道理
（性能分层是真的）。

**收益**（要能说清楚，否则不值得改）：

1. 内核认得的概念少两个 → 承载面变大
2. 血染钟楼那类**并列状态位**（中毒/醉酒/被保护）不必求内核，规则自己加键
3. **身份可写** → 换牌类游戏成立
4. 阿瓦隆这种不用出局的规则，不再为一个用不到的字段付快照与视图的成本
5. 「拦下一次死亡」（白痴翻牌）与「拦下一次任何状态变更」变成同一条路

**代价**（一并写下来，不藏）：

1. 快照格式变更 → golden 快照要重生成，旧存档读不了
2. 一批热路径多一次 map 查找
3. `AddPlayer` 必须发放 `alive` 的初始值（空串等同删除，不发就是「死的」）

### 2.2 迁移次序

内部改完再改外部，每一步都能单独编译通过、单独跑测试：

```
1. 存储层：playerState 只剩 ID + Vars + RoundVars
2. 派生层：PlayerInfo/SelfInfo/PublicPlayerInfo 组装时从键取值填字段
3. 写入层：SET_ALIVE 并进 SET_VAR，保留 NewSetAliveEffect 作为便利构造器
4. 快照层：格式变更 + golden 重生成 + 写迁移说明
5. 身份可写：开放 role 键的写入路径，补「换牌之后 PhaseStep.Role 匹配跟着变」的测试
```

### 2.3 按疤修法

阶段一每一条判定为「抽象问题」的疤，走同一套流程：

1. 修法先写进 `SCARS.md`，说清**为什么这个形状**
2. 改内核
3. 三套规则包全部回归
4. **变异验证**：把新规矩手动改坏，确认有测试变红
5. 疤标记为已关闭，写下关闭时的实际做法与事先猜想的差异

对判定为「人机工程」的疤：**不改内核**，在规则包里写一个辅助函数，
并在 `SCARS.md` 里记下「判定为可接受的绕法」。

### 2.4 §8.2 那四条推测的怎么办

| 缺口 | 处理 |
|---|---|
| 胜负只有一个 `Camp` | 阶段一撞到才改。没撞到就留着——`Winners []Camp` 随时能加，加了撤不掉 |
| 目标只能是玩家 ID | 同上。若选一夜狼人，**大概率会撞到**（中央的三张牌） |
| 组合 `Resolver` | 不做。包装函数够用，两套规则包都没抱怨过 |
| 局中随机 | 撞到才加回。设计原样留在 `SCARS.md` 疤 7 与 `PRIOR-ART.md` |

### 2.5 完成判据

- [ ] 三套规则包全绿，行为无变化（阶段一的规则包也要一起过）
- [ ] `make check` 全绿：build / vet / lint 0 issues / test / race / examples
- [ ] 5000 局 fuzz 全过
- [ ] golden 快照重生成，迁移说明写进 CHANGELOG
- [ ] 每条新规矩都做过变异验证，记录在提交信息里
- [ ] 阶段一的每条疤都已关闭或明确标记「判定为可接受的绕法」
- [ ] `playerState` 上没有除 `ID` 与两张变量表之外的字段

## 阶段四：冻结

### 4.1 「冻结」是什么意思

**不是**「永不改动」。是：

1. 破坏性变更从此需要一条**具体的、撞到过的**理由，不能靠「觉得更好」
2. 每一个导出名都要能回答「谁在用它」——回答不上来的先删（`Rand` 与
   `Metrics` 就是这么删的）
3. 冻结之后加东西要比删东西难：加了撤不掉

### 4.2 冻结前的检查清单

- [ ] 三套规则包，内核零改动地承载
- [ ] 每个导出名都有至少一个非测试使用者，或者能说清为什么留着
- [ ] `DESIGN.md §7`（内核自己拥有的取值）逐条重新辩护一遍
- [ ] `DESIGN.md §9`（不做清单）完整
- [ ] 覆盖率、fuzz、golden 快照、变异验证四条质量线都在 CI 里
- [ ] 命名与授权口径已定（阶段一 §1.2）

### 4.3 版本

**不发版。** 理由已经确认过：

- 零使用者，发布号不通知任何人
- 「不加 `/vN`」的决定意味着 Go 的模块系统**不会**因为主版本号而阻断——
  版本号在这里传达不了「有破坏性变更」这个信息
- 六个版本在一天里发出去过，那是噪音

CHANGELOG 照记，**记的是变更本身，不是发布**。真到了有第一个使用者那天，
再一次性定版本策略。

## 验证方法论（每阶段共用）

这四条是这个项目的质量资产，比任何单条设计更值钱。

### 1. 变异验证——**每条新规矩都要做**

加一条规矩，就手动把它改坏，确认有测试变红。改不红的，说明那条规矩
**只是一句注释**。

这个项目靠它抓到过的真问题：

- 拆掉 `consumeActors` 之后整套测试一条都不红——两套规则包每次都会重新点名，
  陈旧名单永远被覆盖
- 「空串等同删除」改成「写空串」不红——读回来都是空串，差别只在快照里
- 「面向玩家的结构不许有自由格式口袋」当时没有任何东西守着

**做法**：`git stash` 一份，改坏，跑测试，恢复。改坏后测试还绿的，
补测试再来一遍。变异清单写进提交信息。

### 2. 独立的规则包

三套规则包不共用任何取值。加第 N 套时的内核改动量，就是通用性的直接度量。

### 3. 随机对局

5000 局，每局比对：快照往返一致、效果流回放一致、不变量成立。
它抓到过一次「游戏结束时回合数多加了一次」——只在特定 seed 的特定步数上出现。

### 4. 字节级 golden 快照

存档格式漂移立刻变红。阶段二会故意让它变红一次（格式确实变了），
那一次要在 CHANGELOG 里写清迁移。

## 风险与回滚

| 风险 | 征兆 | 应对 |
|---|---|---|
| 阶段二改完发现模型不对 | 第三套规则包为了绕开新模型写出更难看的代码 | 阶段二在独立分支上做；每个迁移小步单独可编译，逐步回退 |
| 第三套规则包一条疤都没撞到 | 阶段二失去输入 | **这是好消息不是坏消息**——说明抽象够用。转去做阶段三、四，§8.2 那四条继续挂着 |
| 快照格式变更影响真实存档 | —— | 目前零使用者，不构成风险。冻结后再变要写迁移工具 |
| 性能回退（变量表查找） | 热路径基准变慢 | 派生只读字段兜底（§2.1）；`make bench` 前后比对 |
| 授权口径没定就动手 | —— | **阶段一的前置条件**，不定不开工 |

## 不在计划内

| | 为什么 |
|---|---|
| 网络层 / 房间 / 匹配 | 宿主的事（[DESIGN.md §1](DESIGN.md) 第三问）。`example/netserver` 是示例，不是产品 |
| AI 玩家 | 同上。内核给的是完整的 `PlayerView`，够任何一个 AI 用 |
| 持久化后端 | `Snapshot` 是纯数据，`json.Marshal` 就是全部接口 |
| 计时 | 引擎不计时，`Timeout` 是建议值。这是刻意的 |
| 性能优化 | 没有任何一个真实负载说它慢。优化在测量之后 |

## 需要你定的三件事

按阻塞程度排：

1. **命名与授权口径**（§1.2）——**阻塞阶段一开工**，且已有的阿瓦隆也要一起处理
2. **第三套规则包选谁**——推荐一夜狼人（正对着两条已有嫌疑的缺口）；
   Secret Hitler 会重开随机那个决定，授权条款也更友好，但需先核实
3. **阶段二要不要提前**——本计划把它排在阶段一之后，理由是避免同一处重构
   做两遍。若你更看重「先把模型摆正」，可以对调，代价是第三套规则包的疤
   会长在新模型上、可能要求再改一次
